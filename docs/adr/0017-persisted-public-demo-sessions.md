# Persisted public demo sessions

The public browser demo now records what it simulates. A visitor's neighbourhood survives a reload, and the ledger can be downloaded over a span of simulated days rather than only the one on screen. This reverses an earlier position — a demo session used to be defined as non-persistent — so the reasons for the reversal, and for the shape it takes, are worth stating.

The demo's data lives in five collections of its own (`demo_sessions`, `demo_runs`, `demo_trades`, `demo_days`, `demo_household_days`) rather than in `simulation_*` and `ledger_events`. Two things make sharing those impossible. Every one of them is keyed by an organisation and written by an authenticated member, which a demo visitor is not and has none of. And `ledger_events` is tamper-evident settlement evidence (ADR 0003) whose worth rests on every row having been authorised; admitting anonymous rows would not extend that guarantee to the demo, it would withdraw it from the ledger. Anonymous demo traffic belongs beside the real ledger, never inside it.

Ownership is a UUID the browser generates and keeps in `localStorage`. There is no account, so this is what lets somebody find their own history and nobody else's, while identifying nothing about them; losing it costs a visitor their history and nothing more. A separate run identifier is minted whenever the scenario resets and is deliberately not persisted, because a reset restarts the simulated day count at one and day 1 of a new run is not day 1 of the last.

Being reachable without a session is the whole point of these routes and also their entire risk, so the server treats everything the browser sends as a claim rather than a fact. Each trade's seal is recomputed from its payload and the browser's version is kept only for comparison; storing the posted hash would make "tamper-evident" a decoration on an endpoint anyone can call. Every write is scoped to its session and refuses a run it does not own, since run identifiers appear in ledger responses and one becoming known elsewhere is ordinary. Request schemas are the whole of the input validation — there is no membership check behind them — and `openapi/coverage.test.ts` pins the set of public routes so that being unauthenticated stays a decision rather than a mistyped flag.

A simulated day is closed exactly once, and a repeated close writes nothing — not the rollup, and not household rows either, since accepting a household the first close never mentioned would be a way to keep appending to a settled day. Stored trades are insert-only. Running the tamper demo alters the browser's copy and leaves the stored rows untouched, which is the demonstration working rather than a gap in it; the day rollup records that it happened. A batch that would leave a gap in the chain is refused rather than sealed onto a predecessor that is not its own, and the head it chains onto is read inside the transaction that appends to it, so two racing flushes cannot both claim it.

Day rollups store no totals. Energy and credit are summed from `demo_trades` on every read, so no second copy exists to disagree with the first. Storing them would mean defending derived figures against every ordering in which a late trade and a day close can interleave — including on a standalone `mongod`, where the two cannot share a transaction at all — and such a defence is worth nothing unless it is perfect. The rollup keeps only what cannot be derived: the day type, the closing rate, the tamper flags, and what the browser claimed together with whether it matched at the moment of closing.

Demo persistence requires a replica set, and declines without one. Every guarantee above is a guarantee about several documents agreeing — a trade and the counter describing it, a rollup and its household rows, a chain head that is still the head when the batch appending to it commits — and a standalone `mongod` cannot promise any of it. Nor can application code supply the missing atomicity: a lock would have to live somewhere, and the only somewhere available is the database that has just declined to provide one. Running these writes anyway would mean offering weaker guarantees than the feature documents, silently, on exactly the deployments least likely to notice. So the routes answer `503 DEMO_PERSISTENCE_UNAVAILABLE` instead and the browser keeps its simulation in memory, which it does perfectly well. Which case applies is discovered by attempting a transaction rather than by inspecting the client, since every real `MongoClient` exposes `startSession` either way.

Persistence is additive, never required. With no `VITE_API_BASE_URL` the browser runs exactly as it did before any of this existed, which keeps the backend-less deployment working and keeps the simulation's own tests free of network fakes. Nothing in the client path throws: an unreachable server leaves trades queued, a permanently refused batch is dropped so the queue behind it can move, and a day whose trades could not be stored is left open rather than closed over figures its own trades contradict.

Everything expires. Every document carries `expiresAt` behind a TTL index bounded by `DEMO_RETENTION_DAYS`, and `DEMO_PERSISTENCE_ENABLED` switches ingest off without shipping new client code. Demo data is disposable by definition and the database it sits in is shared, so unbounded growth is not an acceptable failure mode.
